## Problem Statement

영수증 스캔이 프로덕션에서 죽었다. 원인은 Gemini **지역차단** — Cloudflare Smart
Placement 가 워커를 Gemini 미지원 리전으로 옮기면 `User location is not supported
for the API use` 가 돌아온다. 2026-08-27 06:57 UTC 에 2건 발생.

출발점 질문은 "개인의 Gemini/Claude/GPT **구독**을 쓰게 할 수 없나" 였다.

## 전제 검증 — 두 개가 무너지고 하나가 살아남았다

| 전제 | 결과 |
|---|---|
| 개인 **구독**을 앱이 대신 쓸 수 있다 | ❌ **불가능.** ChatGPT Plus·Claude Pro·Gemini Advanced 모두 API 접근 미포함. 채팅 구독과 API 는 별개 상품·별개 과금 |
| 개인 **API 키**(BYOK)로 바꾸면 지역차단이 풀린다 | ❌ **아니다.** 지역차단은 *누구 키냐*가 아니라 *요청이 어디서 나가느냐*다. 같은 키로 워커가 싱가포르일 땐 성공, 차단 리전일 땐 실패한 것이 실증 |
| **클라이언트에서 호출**하면 지역차단이 풀린다 | ✅ **맞다.** 사용자 브라우저는 한국에 있고 한국은 지원 지역이다. 이 저장소가 이미 해봤다 (커밋 `f497065`: "사용자의 폰은 한국에 있어서 직접 호출하면 문제가 없다. Gemini 가 이 오리진에 CORS 를 허용하는 것도 확인했다") |

**핵심은 사용자가 잡았다.** BYOK 단독은 문제를 못 고치고 클라이언트 호출이 고친다.
그리고 예전에 브라우저 호출을 버린 이유가 *키 노출*이었는데, 각자 자기 키를 쓰면
그 이유가 사라진다. 두 문제가 서로를 상쇄한다.

## 제공자별 브라우저 직접 호출 가능 여부 (조사 결과)

| 제공자 | 브라우저 직접 호출 | 근거 |
|---|---|---|
| **Gemini** | ✅ 가능 | 이 저장소가 `f497065` 에서 실제로 했고 CORS 확인 기록이 있음 |
| **Claude** | ✅ 가능 | `anthropic-dangerous-direct-browser-access: true` 헤더. **BYOK 패턴을 위해 만들어진 기능**이다 |
| **OpenAI** | ❌ 불가 | SDK 의 `dangerouslyAllowBrowser` 는 클라이언트 가드만 끈다. 서버가 `Access-Control-Allow-Origin` 을 안 줘서 CORS 오류 보고가 흔함 |

→ **브라우저 선택지는 Gemini·Claude 2개.** OpenAI 를 넣으려면 워커 경유가 필요한데,
OpenAI 는 지역차단이 없어서 서버 경유해도 안전하다 (범위 밖으로 둔다).

## 제약

- 사용자 2명, 가족 1개. **분당 20회 한도에 걸린 적은 한 번도 없다.** 실제로 물린 건 지역차단뿐
- Gemini 는 두 곳에서 쓰인다: `scan.ts`(영수증 OCR), `shared-recipes.ts`(레시피 검토)
- 푸시 발송 코드가 없다 — 이 기능과 무관하지만 알림으로 안내할 수단이 인앱뿐
- 가족용 앱이다. "AI Studio 가서 키 발급받아 오세요"는 **진입 장벽**이다

## 추천 접근 (승인됨)

**A: BYOK 브라우저 호출 + 공용 키 폴백**

```
스캔 요청
   │
   ├─ 내 키가 있나? ──예──▶ 브라우저가 직접 Gemini/Claude 호출
   │                          (지역차단 없음, 내 한도 사용)
   │                              │
   │                              ▼ 원시 JSON 을 워커로 POST
   │                          워커가 파싱·정규화·저장
   │
   └─ 아니오 ──▶ 지금 경로 (워커가 공용 키로 호출)
                   지역차단 나면 「AI 기능이 일시적으로 중단됐어요」
```

**BYOK 는 의무가 아니라 업그레이드다.** 키를 안 넣은 가족도 지금처럼 쓸 수 있어야 한다.
이게 빠지면 손보경 님은 키를 만들기 전까지 스캔을 못 쓴다.

**원시 응답을 워커로 보내 파싱하는 게 중요하다.** 지금 워커가 `normalizeStorage`,
`shelf_life_days` 기본값, 날짜 계산을 한다. 브라우저로 옮기면 그 규칙이 두 벌이 되고
언젠가 한쪽만 고쳐진다. 호출만 브라우저가 하고 해석은 워커가 계속한다.

## 검토했다가 접은 대안

- **B: 서버 제공자 폴백(앱 키)** — 사용자가 아무것도 안 해도 되지만, 앱 명의로 두 번째
  제공자 계정과 종량제 과금이 생긴다. 사용자가 A 를 골랐다.
- **C: 클라이언트 자동 재시도만** — 작업량은 가장 적으나 근본 원인이 남는다. 긴 장애 때 똑같이 죽는다.

## 확정된 결정 (2026-08-27 후속 세션)

**키는 가족이 공유한다.** 한 사람만 발급받으면 온 가족이 쓴다. 진입 장벽이
크게 낮아지는 대신, 브라우저에만 두는 선택지가 죽는다 — 남의 브라우저에서
읽어야 하므로 서버에 있어야 한다.

**D1 에 AES-GCM 으로 암호화 저장.** 평문은 안 된다 — `wrangler d1 export` 백업이
전체 테이블 평문 덤프라 백업 파일마다 키가 복사된다(`backups/*.sql` 실물 확인).
`SECRET_KEY` 에서 HKDF 로 **세션 서명과 다른 키를 파생**한다. 한 키를 두 용도로
쓰지 않는다. 요청마다 새 12바이트 IV, `base64(iv‖ciphertext)` 저장.
`crypto.subtle` 은 이미 3곳(PBKDF2·HMAC)에서 쓰고 있어 새 의존성이 없다.

**브라우저는 스캔할 때 받고 메모리에만 둔다.** 로그인 시점 수령은 접었다 —
대부분의 접속은 스캔을 안 하는데 키가 세션 내내 남는다. 스캔 시점 수령이면
노출이 한 시간에서 10초로 줄고, 그러면 sessionStorage 를 쓸 이유도 사라진다
(새로고침 생존이 의미 없어짐). Firefox 가 sessionStorage 를 15초마다 디스크에
쓰는 문제도 함께 피한다 — 공용 태블릿에서 크래시 후 다음 사람이 이어받는 시나리오.

**설정에서 키를 다시 읽을 수 없다.** `송인혁의 Gemini ••••4f2a` 로만 보이고
교체·삭제만 된다. 다만 스캔 시 브라우저로 평문이 가므로 가족 구성원은
개발자도구로 볼 수 있다 — **구조적으로 못 막는다.** 숨기는 척하지 않고
"가족끼리 공유하는 키"라고 그대로 말한다.

**키 선택은 사용자가 고른다.** 「교대로」(가장 적게 쓴 키부터, 기본) 또는
「순서 지정」(1순위부터). 어느 쪽이든 429/401 이면 다음 키로 넘어간다.
세는 단위는 스캔이 아니라 **제공자 호출 수(shots)** — 5장 스캔은 5회다.

## 보안 — 네 겹 방어

브라우저가 키를 들고 있다는 사실은 못 없앤다. 호출하는 순간 평문으로 페이지에
존재해야 하고, 그때 JS 를 돌릴 수 있는 쪽은 읽을 수 있다. 패치 가능한 버그가
아니라 그 구조의 정의다. **다만 피해 범위는 되돌릴 수 있는 금전 문제다** —
모델 호출 키일 뿐 가족 데이터에 접근하지 못하고(그건 세션 쿠키 뒤에 있다),
AI Studio 에서 한 번 눌러 폐기·재발급하면 끝난다.

| # | 방어 | 막는 것 | 현재 |
|---|---|---|---|
| 1 | HTTPS 강제 + HSTS | 평문 HTML/JS 중간 변조 → 키 탈취 코드 주입 | ❌ **없음. 이 기능보다 먼저** |
| 2 | CSP `connect-src` | 훔친 키를 공격자 서버로 **보내는** 것 | ❌ 없음 |
| 3 | HTTP 리퍼러 제한 | 훔친 키를 다른 곳에서 **쓰는** 것 | 키 발급 시 설정 |
| 4 | 스캔 시 수령 + 메모리 | 노출 시간 (1시간 → 10초) | 설계에 포함 |

**1번이 지금 뚫려 있다.** `curl http://eatco.dlsgur2845.workers.dev/` 가 리다이렉트
없이 200 으로 앱 HTML 을 평문 전달한다(2,395 bytes). 지금은 세션 쿠키가 `Secure`
라 피해가 제한적이지만, 키를 내려주기 시작하면 카페 와이파이에서 JS 를 바꿔치기해
키를 훔칠 수 있고 **그건 우리 오리진에서 돌기 때문에 리퍼러 제한이 무용지물**이다.

CSP 는 좁게 넣는다:
```
connect-src 'self' https://generativelanguage.googleapis.com https://api.anthropic.com
```

**주의 — 리퍼러 제한을 건 키는 서버 요청을 거부한다.** 그래서 키가 두 종류로
나뉜다: 가족 키(리퍼러 제한, 브라우저 전용)와 앱 공용 키(제한 없음, 워커 폴백용).
지금 구조가 이미 그렇게 되어 있다.

**확인된 TLS 구간:** 브라우저→워커 TLS 1.3(ChaCha20-Poly1305, h2) · 브라우저→Gemini
https 강제 · 워커→Gemini https · 워커↔D1 은 Cloudflare 내부망(직접 검증 불가).

**죽은 설정 주의:** `frontend/nginx/default.conf` 에 CSP `default-src 'none'` 과
Referrer-Policy 가 있지만 **프로덕션 응답에는 없다.** Workers 로 옮기며 nginx 를
안 쓴다. 둘 중 하나라도 살아 있었으면 이 설계가 구현 단계에서 조용히 깨졌을 것이다.

## 스키마

```sql
family_api_keys (
  id, family_id, provider,            -- 'gemini' | 'anthropic'
  label,                              -- '송인혁의 Gemini'
  key_cipher   TEXT NOT NULL,         -- base64(iv‖ciphertext). 평문 절대 금지
  key_hint     TEXT NOT NULL,         -- '••••4f2a' 표시용
  added_by, created_at,
  priority     INTEGER,               -- 「순서 지정」 모드용
  calls        INTEGER DEFAULT 0,     -- 제공자 호출 수 (스캔 수 아님)
  last_used_at, cooldown_until,
  disabled     INTEGER DEFAULT 0, last_error
)
families.key_strategy TEXT DEFAULT 'least_used'   -- 'least_used' | 'priority'
```

```
GET  /scan/key    → 전략에 따라 살아있는 키 하나를 빌려준다 {key_id, provider, key}
POST /scan/parse  → 원시 응답 + {key_id, ok, status} → 파싱·저장·카운터 증가
```

카운터는 **누적**으로 둔다. 월 초기화는 청구 주기와 맞아 매력적이지만 초기화하는
순간 late-join 보정이 사라져 라운드로빈과 같아진다. 대신 설정 화면에
"이번 달 송인혁 62 · 손보경 58" 로 **보여주는 것**으로 공정성을 체감하게 한다.

## 열린 질문

1. **레시피 검토(`shared-recipes.ts`)도 BYOK 로 갈 것인가.** 스캔만 할지, Gemini 쓰는
   두 곳 다 할지. 스캔만 하면 검토는 여전히 지역차단에 노출된다.
2. **키 유효성 확인.** 잘못된 키를 넣으면 스캔할 때 처음 알게 된다. 설정 화면에서
   저장 시 1회 검증 호출을 할지.
3. **2026년 9월 Gemini 키 정책 변경.** 검색 결과에 "9월부터 Standard 키 요청을
   거부하고 auth key 로 옮겨야 한다"는 내용이 있었다. **단일 출처라 미확정** —
   사실이면 다음 달이고 키 기반 설계 전체에 영향을 준다. 구현 전 공식 문서 확인 필수.
4. **Claude 를 고른 사용자의 이미지 처리.** Gemini 와 Claude 는 이미지 입력 형식과
   응답 스키마가 다르다. 프롬프트·파서를 제공자별로 나눠야 한다.

## 성공 기준

- 키를 넣은 사용자는 Smart Placement 가 어디로 가든 스캔이 성공한다
- 키를 안 넣은 사용자는 **지금과 똑같이** 동작한다 (기능 후퇴 없음)
- 파싱 규칙이 여전히 한 곳에만 존재한다

## 배포

기존 `wrangler deploy` 파이프라인이 그대로 덮는다. 새 산출물 없음.

## The Assignment

**키 공유 결정으로 원래 assignment(손보경 님도 키를 만들어야 하나)는 사라졌다.**
한 사람만 발급받으면 온 가족이 쓴다. 그게 이 결정의 값어치다.

대신 남은 가장 싼 검증은 이것이다:

**AI Studio 에서 키를 하나 발급받고, HTTP 리퍼러 제한을
`eatco.dlsgur2845.workers.dev/*` 로 걸어본 뒤, 브라우저 콘솔에서 Gemini 를
한 번 호출해보라.**

이 한 번의 확인이 설계의 3번 방어층 전체를 검증한다. 되면 나머지는 배관이다.
안 되면(리퍼러 제한이 예상과 다르게 동작하면) 방어가 네 겹에서 세 겹으로 줄고,
그건 구현 전에 알아야 하는 사실이다.

코드 한 줄 쓰기 전에 콘솔에서 5분이면 끝난다.
